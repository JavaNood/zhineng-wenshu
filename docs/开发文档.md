# 智能问数 · 开发文档

本文描述当前代码怎么工作。需求来源是 `需求.md`。本体层、业务语义层、专家改名、批处理、本体开关和官方函数调用，都已经落在这条主线上。

数据底座：https://github.com/hccccc01333/powerbi-retail-analysis （7 个 CSV，2023-01 至 2025-12）。

---

## 1. 系统在做什么

用户提一个经营问题。FastAPI 为这一问建立会话，LangGraph 主图驱动主 Agent。主 Agent 通过 DeepSeek 官方 `tool_calls` 读取知识、查看物理列、执行 SQL、把数值报告给用户、列出专家、派工、收口。

分析问题在数值报告之后，主 Agent 从四位专家里选 2 到 3 位。子 Agent 用 `Send` 并行。每位专家先写计划，再在执行阶段调用与主 Agent 相同的查数工具。主 Agent 收回结论后写汇总、共识和分歧。

前端用 SSE 把思考、给用户的步骤、工具卡片、专家计划和证据推到对话里。

在线入口只有主图：`orchestrator.py` → `main_react.py`，专家走 `executors.run_skill_worker` → `plan_execute.py`。`react_graph.py` 里的问数 ReAct 子图仍然存在，工具协议同样是官方 `tool_calls`，但主图不调用它。

## 2. 技术选型

| 项 | 当前实现 |
| --- | --- |
| 知识文件 | YAML。本体层 `ontology/`，业务语义层 `semantic/`。不再加载单一的 `retail_semantic.yaml` |
| 查询 | DuckDB 内存库，启动时把 7 个 CSV 注册成视图。每个子 Agent 独立 `cursor()` |
| 后端 | Python 3.11+、FastAPI、LangGraph。不挂 checkpoint |
| 前端 | React、Vite、TypeScript。开发时 Vite 代理 `/api`；构建后由后端托管 `frontend/dist` |
| 模型 | OpenAI SDK 兼容 DeepSeek。白名单 `deepseek-chat`、`deepseek-reasoner`，默认 `deepseek-reasoner` |
| 工具协议 | 请求带 `tools`。思考在 `reasoning_content`，给用户的话在 `content`，函数调用在 `tool_calls`。带 `tools` 的后续请求把 `reasoning_content` 放回 assistant 消息 |

不引入 WrenAI 引擎、向量库或预聚合立方体。关闭本体时不换成另一套汇总表，也不在提示词里指定一个错误口径。

## 3. 在线链路

```
POST /api/chat
    → Session(question, model, ontology_enabled)
GET /api/stream/{session_id}
    → orchestrate()
        main_turn          一次模型回复：content + tool_calls
          ├─ 没有函数调用，或原因类问题还没派专家就 finish → nudge → main
          ├─ 只有 finish 且允许收口 → finish
          └─ 其他函数 → tools_node（一批，最多 4 个，一次状态更新）
                ├─ dispatch 成功 → worker × N（Send，max_concurrency=3）
                │       → collect_workers → main
                └─ 否则 → main
```

主图节点：`main`、`tools`、`nudge`、`worker`、`collect_workers`、`finish`。没有单独的 ontology 节点。

一次回复里的多个函数在同一个 `tools_node` 里按顺序执行。每个 `tool_call_id` 都有一条 `role: tool` 结果，包括被门闩拦住的和超过 4 个的。图上只回到 `main` 一次。依赖上一次结果的动作不能和提供输入的函数放在同一次回复里。

主循环按模型回复次数计，`MAIN_MAX_TURNS = 32`。一批 3 个工具算 1 次。专家按回复次数计，上限 `MAX_STEPS = 60`。计划最多 `PLAN_STEPS = 20` 步。并行上限 `MAX_PARALLEL = 3`，派工最多 `MAX_SUB_AGENTS = 3`。

## 4. 知识怎么拆

### 4.1 本体层 `ontology/`

只回答业务上有什么、取值是什么、如何相连、必须遵守哪条策略。不写聚合公式。

| 文件 | 内容 |
| --- | --- |
| `entities.yaml` | 订单、订单明细、月度目标、日期、客户、门店、商品。含 grain、标识、属性含义、同义词 |
| `value_domains.yaml` | 销售渠道、大区、客户等级、促销标记、一级类目、支付方式、订单状态、季度等。封闭枚举，或写明取值来自某列 |
| `relations.yaml` | 7 条 many-to-one：订单-日期、订单-客户、订单-门店、明细-订单、明细-商品、目标-门店、目标-日期 |
| `policies.yaml` | `pol_money_display`、`pol_time_grain`、`pol_refund_filter`、`pol_join_whitelist`、`pol_use_certified` |

`pol_use_certified` 要求指标使用认证 code，不在策略正文里写 `SUM` 公式。退款和取消不默认剔除；只要成交订单时，SQL 里显式过滤订单状态，并在结论里注明。join 只能走关系 id。

### 4.2 业务语义层 `semantic/`

| 文件 | 内容 |
| --- | --- |
| `logical_datasets.yaml` | 逻辑数据集 id 等于 DuckDB 视图别名。含来源 CSV、列名、类型、grain、绑定实体 |
| `certified_metrics.yaml` | 基础指标带 `expression`，派生指标带 `formula`，且只能引用已定义的 code |
| `sql_planner.yaml` | 每个认证指标一条规划约束：来源数据集、时间列、允许的关系 id、扇出注意。没有现成 `SELECT` |

认证指标：

| code | 名称 | 口径 |
| --- | --- | --- |
| `sales_amount` | 销售额 | `SUM(实付金额) - SUM(退款金额)` |
| `order_count` | 订单量 | `COUNT(DISTINCT 订单ID)` |
| `gross_profit` | 毛利额 | `SUM(毛利额)` |
| `discount_amount` | 折扣金额 | `SUM(折扣金额)` |
| `gross_margin` | 毛利率 | `gross_profit / sales_amount` |
| `avg_order_value` | 客单价 | `sales_amount / order_count` |
| `discount_rate` | 折扣率 | `SUM(折扣金额) / SUM(商品金额)` |
| `sales_target_rate` | 销售目标达成率 | 销售额 / 销售目标，按门店和年月对齐 |
| `gross_target_rate` | 毛利目标达成率 | 毛利额 / 毛利目标，按门店和年月对齐 |

### 4.3 物理表

`backend/app/db.py` 的视图：

| 视图 | CSV |
| --- | --- |
| `orders` | `fact_订单.csv` |
| `items` | `fact_订单明细.csv` |
| `target` | `fact_月度目标.csv` |
| `d_date` | `dim_日期.csv` |
| `d_cust` | `dim_客户.csv` |
| `d_store` | `dim_门店.csv` |
| `d_prod` | `dim_商品.csv` |

`describe_schema` 对这 7 个视图做 `DESCRIBE`，只返回别名、来源文件名、列名和类型。`ALIAS_DOC` 里的业务短句不进入提示词，也不进入这个工具。

启动时 `validate_ontology()` 同时检查本体层和语义层：基础指标有表达式；派生指标引用的 code 已定义；关系两端的实体属性存在；值域引用的属性存在；规划约束引用的指标、逻辑数据集和关系 id 存在。有问题就在启动日志里列出，不自动改口径。

## 5. 工具与函数调用

`backend/app/tools/schemas.py` 把工具写成 OpenAI function schema。`llm.chat_stream(..., tools=...)` 收集流式 `tool_calls`，按 `index` 拼完参数后再解析 JSON。

`backend/app/tools/batch.py` 的 `classify` 决定这一批里谁执行。`normalize_tool` 仍能把 `name` / `arguments` 收成内部字段，供官方参数和历史写法共用。

### 5.1 目录

本体开启时，主 Agent 的 `tools` 包含：

- 本体：`read_entity`、`read_value_domain`、`read_relations`、`read_policies`
- 语义：`read_logical_dataset`、`resolve_certified_metric`、`read_sql_plan`
- 物理：`describe_schema`
- 编排：`run_sql`、`report`、`list_skills`、`dispatch`、`finish`

本体关闭时，请求里不提供前 7 个知识函数。模型若仍调用，返回「本体访问已关闭」，不读 YAML。

专家只有查数函数：本体四工具、语义三工具、`describe_schema`、`run_sql`。没有 `list_skills`、`dispatch`、`report`、`finish`。专家的收口是正文里的 ` ```conclusion `。

问数子图 `react_graph.py` 的 query 配置只提供 `run_sql`。它不在主图上。

已退出、不再对模型开放的名字：`read_ontology`、`resolve_metric`、`list_dimensions`。

### 5.2 同一次回复的门闩

同批函数看不到彼此的返回。门闩看的是更早回复里已经成立的标记。

| 函数 | 可以执行 | 同批里还有给它提供输入的函数时 |
| --- | --- | --- |
| `run_sql` | 本体开：更早已经成功 `resolve_certified_metric` 且 `read_sql_plan`。本体关：更早已经成功 `describe_schema`。`sql` 必须在参数里 | 先跑那些查询，这条 SQL 记为未执行 |
| `report` | 已有成功 SQL，且 `text` 非空 | 同批有 `run_sql` 时先跑 SQL，这一轮不报告 |
| `list_skills` | 原因、诊断、对比类问题在 `report` 成功之后 | 同批有 `run_sql` 或 `report` 时不列出 |
| `dispatch` | 已 `list_skills`；有 SQL 时必须已经 `report`；有效 `skill_id` 至少 2 个、至多 3 个 | 同批有 `run_sql`、`report` 或 `list_skills` 时不派工 |
| `finish` | 单独一次回复。原因类问题（原因、为什么、为何、下降、诊断、异常）还没派专家时打回，要求先 `list_skills` 再 `dispatch` | 同批还有别的函数时不收口 |

`metric_ready` 只在工具返回里真有口径时置位。`plan_ready` 只在规划列表非空时置位。`schema_ready` 只在返回了带 `columns` 的结构时置位。空结果不会打开 SQL 门闩。

超过 4 个时，前 4 个进入门闩，其余的结果是「单轮最多 4 个工具」。每条未执行结果都写明原因，并要求模型在下一次回复里继续调用。

### 5.3 查询范围

主提示词要求 SQL、`report` 和 `finish` 只覆盖用户点名的指标、时间和维度。用户没点名的渠道、订单状态、门店、商品、客群，不写进 SQL，也不写进报告。

用户要原因、为什么、变化或诊断时，主 Agent 先报告点名的数值，解释交给专家。不用额外 SQL 自己拆解。

函数格式没收到时，nudge 要求改用函数调用，并保持原来的指标、时间和维度，不要扩大成渠道或订单状态拆分。

## 6. 主 Agent

系统提示在 `main_react.main_sys(ontology_enabled)`。它列出当前开关下可用的函数、批处理规则和范围约束。提示词不预写指标公式、枚举和 join 路径。

给用户看的黑色步骤是 `content`。提示词要求只用一两句中文；没有补充时正文留空。`content` 整段推成 `act` 事件，不再从正文里截 ` ```tools ` 或 ` ```sql `。

`tool_calls` 由 `calls_to_pending` 收成内部工具字典，保留 `call_id`。`tools_node` 执行后为每个 id 追加 `role: tool`。派工成功时，这条 tool 结果写「已派出」；专家全部返回后，`collect_workers` 再追加一条 user 消息，内容以「工具 dispatch 的返回」开头，要求下一步 `finish`。

`finish` 的 `summary`、`consensus`、`divergences` 来自函数参数。没查过数也没派专家时，作为寒暄 `chat_answer`。已经 `report` 过、只问数值时，不再重复发一版答案。派过专家后发出 `consensus` 和 `final`。

## 7. 专家

### 7.1 名字

目录 id 不变，页面和派工前言用 title。

| id | title |
| --- | --- |
| `value-price-breakdown` | 量价结构拆解专家-小王 |
| `seasonality-diagnosis` | 时序季节诊断专家-小黄 |
| `benchmark-target` | 目标与门店对标专家-小李 |
| `customer-refund` | 客群与退款诊断专家-小陈 |

`list_skills` 的 `name` 取 title。`description` 包含擅长什么、何时使用、何时不用。`## Instructions` 仍是原来的分析步骤。共识里的 support id 在前端映射成 title。

### 7.2 计划然后执行

`plan_execute.py`：

1. 计划阶段不传 `tools`。模型只输出 ` ```plan `，步骤是取数句子（指标、维度、时间或范围），不把工具名写成步骤。空的 `steps` 数组表示放弃剩余步骤。
2. 执行阶段传入 `worker_tools(ontology_enabled)`。一次回复最多 4 个函数，门闩与主 Agent 相同。
3. 同一次回复里既有函数调用又有新计划时，只执行函数，不改计划。
4. 成功的 `run_sql` 才推进计划下标，并发出 `step_log`。`step` 是计划步骤号，`action` 是该步原文。知识工具不占用勾选。
5. 还有未执行步骤时拒绝 ` ```conclusion `。要提前结束，必须先单独提交 `{"steps":[]}`。
6. 全部取数完成后，工具结果里要求输出结论，末尾用「## 该专家的主要结论」。

前端计划以最新的 `worker_plan` 整份替换。勾选按 `step === n` 或 action 文本匹配，不按「第几次 SQL 涂第几行」。已完成步骤留在计划前面。

达到 60 次回复仍无完整结论时，状态是 `truncated`，结论文本为「达到 step 上限，结论不完整（已中止，不伪造完成）。」不把重复被拒绝的工具调用当成正常结束。

## 8. 问数子图

`react_graph.py` 的 `QUERY_SYS` 要求调用 `run_sql`，不要在正文里写 SQL。拿到结果后，在 `content` 里输出 ` ```conclusion `。SQL 结果以 `role: tool` 回传。

`executors.run_query_point` 会跑这张子图。当前 `orchestrate` 不调用它。问数在主 Agent 里完成：查口径和规划，`run_sql`，`report`，需要时再派专家。

`WORKER_SYS` 仍放在这个文件里，因为 `plan_execute` 用它做专家系统提示。执行阶段的工具调用以 `tool_calls` 为准，不从正文解析工具 JSON。

## 9. 接口与事件

### 9.1 HTTP

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `GET` | `/api/models` | 白名单与默认模型 |
| `POST` | `/api/chat` | 请求体 `question`、`model`、`ontology_enabled`（默认 `true`）。返回 `session_id` |
| `GET` | `/api/stream/{session_id}` | SSE |
| `GET` | `/api/session/{session_id}` | 会话快照 |

`ontology_enabled` 写在该次 `Session` 里。主图从会话读取，不用进程内全局开关。

没有 Key 时，流里发出明确的 `error` 事件，不编造答案。

### 9.2 SSE

| 事件 | 页面用途 |
| --- | --- |
| `reasoning` | 主 Agent 的 `reasoning_content`，灰色可折叠「思考」 |
| `act` | 主 Agent 的 `content`，黑色步骤。连续片段拼成一段 |
| `tool_call` | 工具卡片。未知工具名不渲染 |
| `query_answer` | `report` 的数值答案 |
| `chat_answer` | 寒暄 |
| `agent_start` / `agent_progress` / `worker_plan` / `step_log` / `sub_done` | 专家卡片、计划、SQL 勾选 |
| `consensus` / `final` | 共识、分歧、汇总结论 |
| `tokens` | 该次会话累计的 `prompt`、`completion`、`total` |
| `error` | 失败说明 |

`tokens` 累加主 Agent 与已返回专家的接口 usage。缺失按 0 相加，不另做字符估算。

## 10. 前端

`frontend/src/App.tsx` 是对话页。`useQa.ts` 接收 SSE。`TraceStream.tsx` 渲染思考、步骤和工具卡片。

本体开关在左侧「智能问数」标题正下方，字号 17px，与标题相同。模型选择留在右上角。回答进行中开关禁用。

状态句：

- 还没有对话时，显示在欢迎语中间。开启：「已开启本体知识访问」。关闭：「已关闭本体知识访问能力，Agent回答可信度降低」。
- 第一轮回答结束，或用户在某一轮已经结束后拨动开关，这句话出现在该轮末尾，并随开关立即改字。
- 用户发出下一问时，这句话按当时的开关冻结在上一轮末尾。新的一轮进行中和结束后都不自动再显示。
- 用户在新一轮进行中或结束后再次拨动开关，这句话才出现在这一轮末尾。进行中拨动的，等这一轮结束后显示。

本体关闭并且这一轮已经跑完时，气泡下方另有红字「本轮回答未使用本体知识」。这句按该轮提交时的 `ontologyEnabled` 保留，不因之后拨动开关改到别的轮次上。

用量在该轮气泡下方：`输入 {prompt} tokens · 输出 {completion} tokens`。历史轮各自保留。右侧过程栏不再重复这块数字。

专家卡片、右侧步骤和结论标题都用 `skill_name`。计划勾选跟 `step_log` 的步骤号或 action。

## 12. 约束与验证

- SQL 仅 `SELECT`。关键字预检拒绝写操作和多语句。结果行上限 `RESULT_ROWS = 2000`，同时用于回传和证据。
- 无登录。单次 `ainvoke` 内有效，不挂 checkpoint，不做跨会话记忆。
- 不把演示问题的标准数字写进断言或正则。
- `scripts/smoke_test.py`：两层校验、销售额与客单价口径、四位专家 title、真实 DuckDB 查询、只读拦截。
- `scripts/graph_smoke.py`：主图节点、假模型的 `tool_calls`、报告先于派工、专家计划与 SQL 步对应、单专家异常隔离、60 步截断，以及问数子图的 `run_sql` 工具结果。
