## 0. 一句话方案

用 **Python FastAPI + DuckDB + DeepSeek（OpenAI 兼容）** 搭建一个主从多 Agent 问数服务：主 Agent 做意图理解与 Plan 编排，分析类问题从 **Skill 技能库动态选 ≥2 个 Skill（每位 Skill 即一位分析专家）**，各派一个子 Agent 并行执行，结论并排比较、逐条绑定可回溯证据；前端以 SSE 流式展示思维链、步骤进度、工具调用与口径。

## 1. 调研结论与选型

### 1.1 本体（指标语义层）格式
调研了三类开源/工业做法，结论：**采用轻量 YAML 语义层**，不引入 WrenAI 的 Rust 语义引擎、不做 RAG。

| 参考 | 可借鉴点 | 本项目取舍 |
| --- | --- | --- |
| WrenAI MDL（Modeling Definition Language） | 业务含义显式落文件、模型/关系/计算字段可版本化 | 借鉴"显式语义契约"理念，去掉 Rust 引擎与向量记忆 |
| 阿里 DataWorks 语义模型 YAML | `instructions`、`metrics(name/synonyms/expression)`、`metric_formulas`、`datasets(表/字段/同义词)` 四段结构 | 直接采用此四段式 + 关系白名单 |
| MetricFlow / SelectDB 语义模型 | 实体、维度（time/categorical、时间粒度）、度量分离 | 借鉴维度时间粒度与度量定义 |
| 墨天轮 sem_metric 工程实践 | 可加性 `additivity`、默认过滤 `filter_expr`、允许下钻维度 `dims`、关系 join 白名单、枚举值单独可查 | 全部纳入本体字段，防止 LLM 瞎 join、瞎求和 |

### 1.2 可参考的开源项目（只借目录与分层，不引入重型依赖）
- **WrenAI**：Next.js UI + Python/FastAPI Service + 语义引擎；分层清晰，但 AGPL、Rust 引擎过重，仅参考"上下文与执行分离"。
- **Vanna（RAG-first）/ DB-GPT（多 Agent 工作流）**：作为范式参考，不直接依赖。
- **FastAPI 全栈脚手架 / LangGraph supervisor 示例**：参考 `backend/app/{api,core,agents,tools,services}` 与 `frontend/` 的分层；主从编排参考 supervisor 模式（中心协调者派发给 worker）。

### 1.3 关键技术选型（已对齐需求 D1–D5）

| 项 | 选型 | 理由 |
| --- | --- | --- |
| 本体形态 | YAML 指标语义层（D1） | 轻量、可人工审阅、Git 可版本化 |
| 查询引擎 | DuckDB 原生查 CSV（D2） | `read_csv_auto` 零导入，5 万行秒查，只读 |
| 后端 | Python 3.11+ / FastAPI（D3） | DeepSeek 生态、SSE 流式、依赖轻 |
| 前端 | React（Vite + TS）（D3 轻量 Web） | 组件化便于步骤面板/证据锚点/模型选择器复用；前后端分离标准结构 |
| 编排 | **自研轻量 supervisor**（asyncio 信号量=3） | 初版不引入 LangGraph，降低依赖与调试成本；预留 LangGraph 增强位 |
| LLM | DeepSeek，OpenAI SDK 兼容，**模型前端可选** | base_url `https://api.deepseek.com`；thinking 的 `reasoning_content` 作为思维链来源；可选模型列表由后端配置 |
| 分析意图 | Skill 技能库动态选 ≥2 个（D4） | 不写死固定专家，Skill 卡片可扩展，每个 Skill 对应一位分析专家 |

> 编排取舍说明：LangGraph 能提供状态图与 checkpoint，但本 Demo 是单次对话、流程固定（意图→Plan→并行→汇聚），自研 supervisor 用 `asyncio.gather` + 信号量即可满足"并行度≤3、step≤60"，可读性和可控性更高。若后续需要循环反思/人工介入，再引入 LangGraph。

## 3. 本体（指标语义层）设计

### 3.1 文件与位置
- 文件：`ontology/retail_semantic.yaml`，由 LLM 读 CSV 表头 + README 按模板生成，**人工逐项校验后定稿**。
- 加载：启动时一次性读入内存，提供给 `read_ontology` / `resolve_metric` 工具。

### 3.2 YAML 结构（字段约定）

```yaml
# ontology/retail_semantic.yaml
meta:
  domain: 中国新零售经营分析
  description: 订单、商品、客户、门店、渠道与月度目标的星型模型语义说明
  data_range: "2023-01 ~ 2025-12"
  currency: CNY

instructions: |
  金额单位为人民币元；销售额口径=实付金额−退款金额；
  分析默认只看有效订单，退款/取消需单独说明；时间表达必须落到 dim_日期 的明确年月/季度。

metrics:                      # 标准指标（问数意图必须命中此处，禁止 LLM 自造口径）
  - code: sales_amount
    name: 销售额
    synonyms: [销售额, 营收, 成交额, 收入]
    expression: "SUM(实付金额) - SUM(退款金额)"
    additivity: additive       # additive / semi / non；金额可加，余额类不可跨期加
    filter_expr: null          # 默认过滤，如排除内部单；本数据集暂无
    dims: [channel, region, store, category, customer_grade, month, quarter]
    unit: 元
  - code: order_count
    name: 订单量
    synonyms: [订单数, 单量, 成交订单数]
    expression: "COUNT(DISTINCT 订单ID)"
    additivity: additive
    dims: [channel, region, store, month, quarter]
  # …毛利额、毛利率、客单价、折扣率、销售/毛利/订单量目标达成率

metric_formulas:              # 派生指标（基础指标组合）
  - name: 客单价
    formula: sales_amount / order_count
  - name: 毛利率
    formula: gross_profit / sales_amount

datasets:                     # 表与字段
  - source: fact_订单
    description: 订单级交易事实表（50000 行）
    fields:
      - name: 订单ID
        type: varchar
        desc: 订单唯一编号，去重计数用
        synonyms: [订单号]
      - name: 实付金额
        type: double
        desc: 客户实际支付金额
      # … 其余字段逐一登记类型/含义/同义词
  - source: dim_门店
    description: 门店维度（38 家）
    fields: [大区, 省份, 城市, 渠道类型, 开业日期]

dimensions:                   # 可下钻维度与枚举（供 LLM 查取值，避免猜枚举）
  - code: channel
    name: 销售渠道
    values: [线下门店, 天猫旗舰店, 抖音小店, 京东自营, 拼多多, 企业团购]
  - code: region
    name: 大区
    values: [华东, 华南, 华北, 西南, 华中, 东北, 西北]
  - code: customer_grade
    name: 客户等级
    values: [普通, 银卡, 金卡, 黑金]
  - code: promo
    name: 促销标记
    values: [日常, 大促, 会员日]
  - code: category_l1
    name: 一级类目
    values: [家电, 数码, 美妆, 食品, 服饰, 母婴, 家居]

relationships:                # join 白名单：只允许这些路径，禁止 LLM 临场猜 join
  - from: fact_订单.订单日期
    to: dim_日期.日期
    type: many-to-one
  - from: fact_订单.客户ID -> dim_客户.客户ID
  - from: fact_订单.门店ID -> dim_门店.门店ID
  - from: fact_订单明细.订单ID -> fact_订单.订单ID
  - from: fact_订单明细.商品ID -> dim_商品.商品ID
  - from: fact_月度目标.门店ID -> dim_门店.门店ID
  - from: fact_月度目标.年月 -> dim_日期.年月
```

### 3.3 本体校验规则（开工后人工/脚本核对，不写死答案）
- 每个 metrics 必须有 `expression / additivity / dims`；派生指标只能引用已定义基础指标。
- 每条 relationships 的两端表/字段必须在 datasets 中真实存在。
- `dimensions.values` 必须与 CSV 实际枚举一致（首次构建后抽查）。
- 指标口径与需求文档第六节 8 个核心口径逐一对照，不得漂移。

## 4. Agent 编排设计

### 4.1 角色与约束
- **主 Agent（Supervisor）**：接收问题、意图理解、任务规划、派发子 Agent、监控进展、沟通回溯、汇总输出。
- **子 Agent（Worker）**：执行单个 Skill（一位专家）/单条查询，可并行；**最大并行度 3**；**单 Agent step 上限 60**（编排层计数，超限中止该子任务并在结果中标注，不伪造完成）。
- 无长短期记忆，单次对话有效；无登录。

### 4.2 意图理解（三分类）
主 Agent 把问题按点拆分，每点归类：
- **对话意图**：寒暄/确认/非数据问题 → 直接回答，不查数。
- **问数意图**：查询指标/数值 → `查本体 → 确认指标 → 形成 SQL → 执行 SQL → 返回结果`。
- **分析意图**：解释变动/诊断异常/对比 → `查技能库 → 动态适配 ≥2 个 Skill → 各 Skill 形成 Plan → 子 Agent 执行 → 汇总`。

示例："2025 年销售额如何？环比 2024 年如何？销售额为什么变动？" 拆为 2 个问数点 + 1 个分析点。

### 4.3 Plan 结构（前端可见、可执行）
每个问题点生成结构化 Plan（JSON），含：`intent`、`goal`、`steps[]`（`step_id / action / 依赖 / 取数规格 / 产出`）、`status`。分析点的每个被选 Skill 是一条独立子 Plan，Skill 间无强依赖则并行；分析类须先完成"总量确认"（本期/对照期总量），再按 Skill 并行下钻。

> 意图理解规则（需求九.2）：意图三分类的判定提示词与 few-shot 示例放在 `agents/planner.py` 的提示词模板中维护，不单独建 Skill 卡；它是主 Agent 的路由规则，不是可并行的专家 Skill。

### 4.4 子 Agent 并行与汇聚
- `asyncio.Semaphore(3)` 控制并发；`asyncio.gather` 并行执行，单任务 step 计数 ≤60。
- **汇聚**：合并各子 Agent 结论，标注
  - **共识项**：≥2 个 Skill 指向同一拖累/结论；
  - **分歧项**：结论不一致，挂起待复核，不强行合并；
  - 每条结论挂证据：本体指标定义、执行 SQL、结果快照、口径公式。

### 4.5 关于"不做降级策略"的边界
需求要求不设降级：禁止用规则/正则/固定话术绕过 LLM 直接给答案。**SQL 执行报错属于正常执行循环**，允许子 Agent 在 step 上限内根据错误信息修正 SQL 后重试；这不叫降级。但不允许"LLM 失败就返回写死的示例答案"。

## 5. 工具系统设计

工具触发采用 **ReAct 式代码块协议**：LLM 在回复中输出 ```sql 代码块，执行循环正则提取后内联调用 `run_sql`，把列/行结果回喂，LLM 决定下一步；完成后输出 ```conclusion 收口。本体读取、指标对齐、Skill 列举等只读目录工具经 `tools/registry.py` 分发（注册表预留 function calling 扩展位）。全部工具只读、可回溯。子 Agent 仅开放其 Skill 所需的 `run_sql / resolve_metric` 等子集。

| 工具 | 职责 | 输入 → 输出 |
| --- | --- | --- |
| `read_ontology` | 读取语义层（表/字段/指标/关系/枚举） | 可选主题 → 相关本体片段 |
| `resolve_metric` | 自然语言指标对齐标准指标与口径 | "营收" → sales_amount + 表达式 + 允许维度 |
| `run_sql`（执行循环内联） | DuckDB 只读执行，返回列、行、SQL 快照 | ```sql 块 → {columns, rows, sql, row_count} |
| `list_skills` | 列出技能库可用分析 Skill（专家，读 frontmatter） | 无 → Skill 卡片摘要列表 |
| `merge_results`（主 Agent） | 汇聚、标共识/分歧 | 各子结论 → 共识/分歧清单 |

`run_sql` 安全约束：仅允许 `SELECT`；拒绝写操作/多语句；语句经关键字预检；结果与 SQL 原文落会话快照。

## 6. 技能库（Skill 库）设计（动态选 ≥2 个）

### 6.0 概念：Skill 与 Method 的关系（回应"为什么不是 methods 而是 skills"）
- **Skill（技能包）= 一位分析专家的完整能力卡**，是对外封装与演示叙事的单位，采用 Anthropic 官方 `SKILL.md` 形态：frontmatter（name/description/trigger 等做 L1 发现）+ Markdown 正文（`## Instructions` 执行指引、`## Examples` 示例、产出与校验做 L2 触发后加载）。
- **Method（分析套路）= Skill 内部承载的具体分析方法**（量价拆解、季节诊断、目标对标、客群退款），是 Skill 的内容实质，写在该 Skill 的 Instructions 里，不再单独成目录。
- 因此"Agent + Skill 模拟不同专家"落地为：分析问题由主 Agent 从 `skills/` 动态选 ≥2 个 Skill（≥2 位专家），各派一个子 Agent 并行执行，结论汇聚比较。**Skill 不是被取消，而是从别名"方法"正名回项目目标里的 Skill。**
- 边界：意图理解、本体读取、SQL 查询是通用工具/路由能力，其行为规则（格式、红线、工具协议）属框架层，写在 `agents/` 与 `tools/` 的系统提示中，**不放进 `skills/`**；`skills/` 只装可并行的分析专家技能（"做什么、何时触发、怎么拆"）。

### 6.1 Skill 卡格式（官方 `SKILL.md`，目录式：`skills/<kebab-name>/SKILL.md`，一 Skill 一目录）

采用 Anthropic Agent Skills 标准：**YAML frontmatter 负责"发现与选择"，Markdown 正文负责"触发后加载执行"**。

- frontmatter：`name`（kebab-case 小写连字符，≤64，技能唯一标识）、`title`（中文展示名）、`description`（≤1024，写清"做什么 + 何时触发 + 何时不用"）、`trigger`（触发关键词）、`expert_role`（专家角色）、`inputs`、`output_schema`、`validation`。
- 正文：`## Instructions`（分步执行指引）、`## Examples`（示例）、`## 产出与校验`；正文控制在 500 行内。

```markdown
<!-- skills/value-price-breakdown/SKILL.md -->
---
name: value-price-breakdown
title: 量价结构拆解专家
description: 量价结构拆解专家。当销售额/收入环比或同比下降，需要先判断是"订单量变少"还是"客单价下降"，再沿渠道、大区、门店、类目定位责任模块时使用；不适用于纯季节性判断或目标达成率评估。
trigger: 销售额/收入下降且需定位责任模块
expert_role: 经营诊断专家，专看"量（订单量）"与"价（客单价）"对销售额变化的贡献
inputs: [本期窗口, 对照窗口, 指标=sales_amount]
output_schema: {量价分解表, 渠道/大区/类目贡献排序}
validation: 各维度贡献占比之和=总降幅；量效应+价效应=Δ销售额
---

# 量价结构拆解专家

## Instructions
1. **定窗口与总量**：取本期、对照期的销售额、订单量、客单价（口径一律以本体为准），计算 Δ销售额、Δ订单量、Δ客单价。
2. **量价连环替代闭合**：量效应 = Δ订单量 × 上期客单价；价效应 = Δ客单价 × 本期订单量；二者之和 = Δ销售额，需闭合校验。
3. **渠道下钻**：按销售渠道分组环比，算各渠道贡献占比。
4. **大区/门店下钻**：定位贡献最大的拖累区域与门店。
5. **类目结构迁移检查**：订单明细 join dim_商品，看一级/二级类目结构迁移。
6. **折扣率对比**：折扣金额/商品金额，检查让利是否侵蚀客单价。

## Examples
- 问题"2025Q4 销售额环比 Q3 下降"：先算两期总量与量价效应，再按渠道、大区、类目逐层定位。

## 产出与校验
- 产出：量价分解表、渠道/大区/类目贡献排序。
- 校验：各维度贡献占比之和=总降幅；量效应+价效应=Δ销售额，不得拆不闭合。
```

### 6.2 初版内置 Skill（4 位专家，演示跑通，后续扩充）
1. `value-price-breakdown` 量价结构拆解专家：量/价分解 + 渠道/大区/门店/类目下钻 + 折扣影响。
2. `seasonality-diagnosis` 时序季节诊断专家：月度分解、历史季节对照、μ±2σ 波动显著性、促销节奏对齐。
3. `benchmark-target` 目标与门店对标专家：三项目标达成率、门店缺口排名、毛利对照、同比剔除季节。
4. `customer-refund` 客群与退款诊断专家：新客首单占比、客户等级/企业客户贡献、退款取消占比预警。

> Skill 由 LLM 依据问题从 `list_skills`（读 frontmatter 的 id/name/trigger/description）中动态选 ≥2 个，不写死"必选哪几个"；选中后才把该卡正文（Instructions）注入子 Agent。

## 7. 数据查询层（DuckDB）

- 连接：内存库 `duckdb.connect(":memory:")`；**每个子 Agent 独立 `cursor()`**（连接非线程安全）。
- 取数：`read_csv_auto('data/CN_Ecommerce_Ops/fact_订单.csv', SAMPLE_SIZE=20000)` 自动推断类型；常用表在启动时注册为视图别名，简化 SQL。
- 只读：工具层拦截非 SELECT；不建持久化库、不写 CSV。
- 结果快照：SQL 原文、时间窗、列、行一并存会话 JSON，供前端点击回看。

## 8. 前后端设计

### 8.1 API（FastAPI）
- `POST /api/chat`：发起对话，请求体含 `question`、`model`（可选，命中白名单，缺省用默认模型），返回 `session_id`。
- `GET /api/stream/{session_id}`：SSE 推送事件。
- `GET /api/session/{session_id}`：回看会话快照（证据引用）。

### 8.2 SSE 事件协议（前端按类型渲染）
| 事件 | 内容 |
| --- | --- |
| `intent` | 意图拆分结果（对话/问数/分析） |
| `plan` | 生成的 Plan 步骤树 |
| `agent_start` / `agent_progress` / `agent_done` | 子 Agent 启动、进度、完成（并行并排展示） |
| `tool_call` / `tool_result` | 工具名、入参、返回摘要、证据锚点 |
| `consensus` | 共识 / 分歧清单 |
| `final` | 汇总结论 + 口径 |
| `tokens` | 输入/输出 token 统计（DeepSeek 末 chunk usage 累加） |

### 8.3 前端界面（对齐需求第七节）
1. **思维链**：DeepSeek thinking 的 `reasoning_content` 以可折叠块展示（同款风格）。
2. **步骤面板**：右上角/侧边展示当前问题 step；子 Agent 并行时并排卡片 + 进度态，可展开/关闭。
3. **阶段化返回**：每阶段展示工具调用与执行步骤；结论后挂"（1）"等锚点，点击展开本体片段 / SQL / 结果快照。
4. **口径展示**：最终列出涉及指标的计算方式。
5. **Tokens 统计**：单次对话结束展示输入/输出 tokens。
6. **模型选择器**：对话区提供模型下拉（可选模型白名单），切换后后续对话使用所选模型，当前会话即时生效。

### 8.4 LLM 接入（模型前端可选）
- OpenAI SDK：`base_url="https://api.deepseek.com"`，`api_key` 读环境变量 `DEEPSEEK_API_KEY`。
- **模型做成可选**：`config.py` 维护可选模型白名单（如 `deepseek-chat` / `deepseek-reasoner` / `deepseek-v4-pro` / `deepseek-flash`），前端 `ModelPicker` 下拉选择并随请求回传；后端校验命中白名单，非法值回退默认，不接受任意模型名。
- `stream=True` 接 SSE；`stream_options.include_usage=true`，末 chunk 取 `prompt_tokens/completion_tokens/total_tokens` 累加。
- 思维链取 `reasoning_content`，正式答复取 `content`。

## 10. 开发步骤（审核通过后执行，已补充细化顺序）

1. **环境与骨架**：建目录、`requirements.txt`（fastapi/uvicorn/openai/duckdb/pyyaml/pandas）、`frontend/package.json`（react/vite/typescript）、`.env.example`、`.gitignore`。
2. **数据落地**：下载 7 个 CSV 到 `data/CN_Ecommerce_Ops/`，核对行数与表头（50000/87635/1368/1096/8000/38/108）。
3. **本体构建**：LLM 读表头+README 生成 `retail_semantic.yaml`，按 3.3 校验规则人工定稿。
4. **LLM 与配置层**：`config.py`（含可选模型白名单/默认模型）+ `llm.py`，打通一次非流式调用与 tokens 读取。
5. **工具层**：本体工具 → `run_sql`（只读预检+快照）→ `list_skills` 技能列举。
6. **主 Agent**：意图三分类、Plan 生成、问数链路跑通（单轮问数先通）。
7. **Skill 库 + 子 Agent**：落 4 个 Skill 卡，实现 worker 并行（信号量 3）、step 计数 60。
8. **汇聚**：共识/分歧标注、证据锚点、口径输出。
9. **后端 SSE**：按 8.2 事件协议逐级推送。
10. **前端（React/Vite）**：搭工程骨架，实现思维链、步骤面板（并行并排）、阶段引用、口径、tokens 五块 + 模型选择器；与后端 SSE 联调。
11. **联调与演示脚本**：用"2025Q4 销售额环比 Q3 下降原因"等 2–3 个案例走全链路。
12. **README 与收尾**：运行说明、目录说明、演示话术。

> 测试策略（对齐需求 D5）：只做结构/契约/连通性校验（本体能否加载、SQL 是否只读、SSE 事件是否齐全），**不写死标准答案、不用正则伪造结果验收**；效果验证靠真实 LLM 实跑。

## 11. 可开发性自审（审核重点）

### 11.1 可行性核对
| 需求点 | 落地方式 | 是否可行 |

| 无登录 / 单次对话 / 无降级 | 内存会话、不写死答案 | 可行 |

### 11.2 风险与缓解
| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| LLM 生成 SQL 方言/join 出错 | 查数失败 | 本体关系白名单 + 仅 SELECT 预检 + step 内修正重试；不降级给假答案 |
| 不同 Skill 结论冲突 | 汇聚困难 | 显式标"分歧项"挂起，不强行调和 |
| DuckDB 连接并发 | 非线程安全 | 每子 Agent 独立 cursor |
| 明文 Key 泄露 | 安全 | 仅 `.env`，`.gitignore` 排除，文档不记录 |
| 单页上下文超长 | 超 token | 本体按需片段注入，不全量塞提示；step≤60 兜底 |
